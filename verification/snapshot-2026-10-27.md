# How this snapshot was verified

27 October 2026. Every figure in the [README](../README.md) comes from one of
the checks below: a command run on the machine, a request to a running service,
or an HTTP request to the upstream project. Where a claim could not be checked
at the time, it is listed instead of quietly asserted.

Both cards are on the PCIe bus with no interconnect between them, which is why
models are split by layer. The processor name, core count, and memory totals
come straight from the kernel and firmware; the driver and toolkit versions from
the installed packages.

## The inference engine

```console
$ build/bin/llama-server --version
version: 0.4.1-dev (build 10988, commit 9f31776c3)
$ git -C src/llama.cpp describe --tags
b10988
$ curl -s http://127.0.0.1:8080/props
{"role":"router","max_instances":1,"models_autoload":true,...,"build_info":"b10988-9f31776c3"}
```

The engine is [llama.cpp at the commit linked in the README](https://github.com/ggml-org/llama.cpp/commit/9f31776c3773cf03f98535c19b7e6d394af374b4),
built with CUDA and Flash Attention for both GPU architectures. The build flags
were read from the generated CMake cache, not from documentation: CUDA on, Flash
Attention on, the all-quants variant off, targets 8.9 and 12.0. The router
reports itself as a router with a single instance and autoloading enabled.

## The model catalogue

`GET /v1/models` returned three entries, all unloaded, which confirms that
nothing is preloaded and the router really does idle at zero VRAM.

The context sizes, cache types, tensor splits, multi-token prediction settings,
and runtime flags in the README were read twice: once from
[`config/profiles.json`](../config/profiles.json), and once from the resolved
launch arguments the router reports for each model. The two agree for all three
profiles. That second source matters because it is what the running process
actually received, after every default has been applied.

The Sakura model needs a caveat. The revision recorded when the weights were
downloaded no longer resolves: the Hub returns 404 for it, because that

bytes. Local integrity still rests on the hashes in the manifest, which are
unaffected by an upstream rewrite.

## The replication package

The recipe under [`setup/`](../setup/README.md) was assembled from this running
configuration, then checked as far as the recording environment allows.

| Check | Result |
|---|---|
| Shell syntax, all seven scripts | pass |
| `install-router.sh` rendering | substituted paths into `runtime/models.ini` and reported every referenced file present |
| Router started from the rendered preset, with no local tooling | pass: `llama-server --models-preset … --models-max 1` on an alternate port reported role `router`, `max_instances 1`, and the three expected model ids |
| `preflight.sh` | ran; correctly failed the GPU probe in this shell and warned about the missing `hf` CLI |
| `verify.sh` against the live services | pass: router, three model ids, both web services, and three weight hashes read back from disk |

All four download hashes were recomputed on 27 October and match both the
manifest and the profile record:

| File | SHA-256 prefix |
|---|---|
| Swift 1.5 Qwen3.8-27B Q4_K_S | `46a360c2…` |
| F16 projector | `daa1116c…` |
| Gemma-4-31B QAT Q4_0 | `b51c17e9…` |
| Gemma chat template | `ae53464b…` |

The image stack was checked the same way while the stack was stopped, so these
are checks of files and checkouts, not of a running service:

| Item | Result |
|---|---|
| ComfyUI checkout | at the pinned release commit, tag `v0.37.0` |
| ComfyUI-GGUF checkout | at the pinned commit |
| Diffusion model, text encoder, VAE | all three SHA-256 values match the image manifest |

Not executed while preparing the recipe: a clean-machine run of the whole
sequence, the build script (a working build already existed), the download script
(the weights were already present, so the hashes were verified instead), the
Podman install path (no usable container runtime in this shell), starting
ComfyUI, and the `--load` branch of the verification script, which needs working
GPUs.

## What could not be verified

| Item | Why, and what it means |
|---|---|
| GPU memory in use, PCIe topology, peer-access test | The recording shell had a minimal `/dev` with no NVIDIA device nodes, so `nvidia-smi` could not reach the driver and CUDA initialisation failed. This is a limitation of that shell, not a fault: the driver module is loaded, its version file resolves, both cards are on the bus, and both are serving inference. The 16 GB figures are the rated capacity of each card. |
| Benchmark figures, throughput, latency | Out of scope. No inference was run to produce this snapshot. |

## What was removed for publication

- Absolute home-directory paths, from the configuration and from the
  provenance entries. Pointers to local evidence files were dropped rather than
  rewritten, since they would be dead links either way.
- GPU device identifiers, replaced by neutral slot names wherever they appeared,
  including as keys in the KV-cache experiment policy.
- Container image digests. The deployment pins both images by digest; this copy
  records versions and tags only.
- Logs, backups, runtime state, model weights, and benchmark artefacts, none of
  which are included.
